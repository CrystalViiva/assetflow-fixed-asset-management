## Architecture reviewed

Django and PostgreSQL remain authoritative for authentication, organization scope, domain state, accounting, reports, assurance, audit, and dashboard aggregates. React uses strict DTOs, authenticated repositories, TanStack Query and session-generation fencing. Live reports are current queries. Snapshots are durable captures; `as_of` means capture time, not arbitrary historical reconstruction. Exports render only completed snapshots and are served through authenticated private-content endpoints.

The operational dashboard uses bounded live Django/PostgreSQL aggregates. Airflow extracts versioned snapshot data as JSONL; PySpark consumes versioned contracts and writes curated Parquet marts. The browser does not read those files. DAG parsing/contracts were tested, but no deployed Airflow scheduler or Spark runtime was available for execution validation.

The source review covered auth/users/RBAC, organization references, assets/categories, acquisition/capitalization, accounting periods and SLM schedules/entries, custody/transfer, maintenance, disposal, verification/evidence, assurance, reports/snapshots/exports, audit, dashboard, OpenAPI, frontend repositories/DTOs/screens, and their associated regression suites. Existing milestone tests cover domain-specific state transitions, constraints, rollback, tenancy, permissions, and failure handling. The unified smoke below crosses the major financial, operational, control, reporting, and evidence boundaries on the same asset.

## Golden lifecycle and accounting reconciliation

A fresh PostgreSQL 17 cluster was initialized under the operating-system temporary directory, bound to loopback on port 55439, with a throwaway role. It was separate from the persistent application PostgreSQL service. The F16 runner created and dropped a random `assetflow_f16_*` database and a temporary private evidence/export directory. Django migrations, actual HTTP APIs, and TypeScript repositories were used; no mock repositories or direct fixture writes created domain/audit events. Celery tasks ran in isolated eager mode.

Reproduction entry point: `.\venv\Scripts\python.exe scripts/f1-smoke.py --f16` after configuring the smoke runner for a disposable PostgreSQL server. The smoke runner creates/drops its uniquely prefixed database and private storage; it must not be pointed at the persistent application database.

One asset traversed:

- organization/reference setup; asset manager, approver, and custodian identities;
- draft asset, componentized acquisition, capitalization;
- SLM schedule and January posting;
- custody assignment, approved/completed placement transfer, return;
- maintenance work order, assignment/start, rounded cost and immutable completion;
- verification campaign, deliberate tag discrepancy, NOTE metadata and PNG upload/download;
- completed FULL assurance execution, public finding occurrence, review/resolution when a public finding existed;
- live asset-register report, completed schema-v1 snapshot, CSV and JSON export;
- separate administrator approval and disposal completion;
- post-disposal dashboard, live report, snapshot immutability and audit checks.

Independent Decimal oracle:

- Capitalized cost: `1,000.01 + 0.99 = 1,001.00`.
- Residual: `100.00`; useful life: 36 months; SLM monthly amount: `(1,001.00 - 100.00) / 36 = 25.0277...`, ROUND_HALF_UP to `25.03`.
- Posting: opening `1,001.00`; expense `25.03`; accumulated `25.03`; closing/book value `975.97`. Identity: `1,001.00 - 25.03 = 975.97`.
- Maintenance: `2.500 × 13.37 = 33.425`, ROUND_HALF_UP to `33.43`; the asset's capitalization, residual, life, method, accumulated depreciation and book value were unchanged.
- Disposal proceeds `1,200.00`; carrying amount `975.97`; gain `224.03`. Asset became DISPOSED and the posted depreciation row remained intact. The post-disposal dashboard reported 0 currently held assets, 1 disposed asset, and held-portfolio book value `0.00`.

Transfer changed department/location only after completion and preserved the active assignment. Return closed custody while retaining transferred placement. Verification and assurance left asset master and financial values unchanged. The golden script verifies these source and final states through API and database/storage readback checks.

## Reporting, dashboard, evidence and audit

The golden asset's live report and dashboard returned exact strings `1001.00`, `25.03`, and `975.97`. A schema-v1 snapshot captured the ACTIVE row. After disposal, the live report became DISPOSED while the old snapshot row remained ACTIVE. CSV and JSON exports were completed from that snapshot; their source UUID, byte size and SHA256 were checked, and downloaded bytes matched stored artifacts. JSON retained the versioned envelope. Private storage keys were used only by the disposable server verifier, never by browser requests.

A valid PNG was uploaded with a deliberately misleading client MIME type. Django returned VERIFIED evidence; the authenticated download bytes matched upload bytes, size and SHA256. Binary evidence was verification-owned, distinct from NOTE metadata. F16 did not create a generic asset document store. Validation is structural/type and integrity validation, not malware scanning.

Backend-generated audit events were checked for capitalization, depreciation, transfer, work completion, evidence verification, snapshot/export completion and derecognition. Audit is application-level append-only history, not a cryptographic ledger. Existing API smokes/test suites cover authenticated private downloads, foreign UUID denial, audit read-only behavior, redaction and tenant/role scope.

Existing F13 backend regression tests exercise bounded Decimal aggregates, tenant/department scope and child-row multiplicity. Existing F9 tests/smokes cover snapshot idempotency and immutability; export attempt fencing and integrity. Existing F8 tests cover frozen inputs, candidate isolation, atomic publication, recovery, occurrences and review/resolution. No live Airflow/Spark runtime is claimed.

## Security and failure review

The source and tests reviewed tenant derivation, organization-scoped object lookup, department-scoped dashboard/report behavior, role permissions, serializer writable fields, direct UUID/detail/content endpoints, F11 privilege-field injection, session generation and mutation retry behavior. F1-F14 disposable API smokes exercised the milestone-specific tenant, RBAC, IDOR, private-file, session and workflow boundaries. The F16 fixture independently used a separate approver for disposal and verified no browser-supplied organization or storage path was needed. No requests targeted third-party systems or the persistent application database.

Critical mutation services use transactions, locks and/or database constraints appropriate to the workflow. Repeated capitalization, same-period depreciation, transfer, maintenance, disposal and workflow actions are covered by milestone API/backend tests. Assurance duplicate delivery/recovery/publication, snapshot idempotency, export fencing and rollback have focused backend regression coverage. The F16 unified smoke itself is sequential; concurrent HTTP races were not load-tested.

### Contract defect fixed

**F16-001 (P1, fixed):** The strict assurance-finding DTO rejected a valid public finding that referenced both its registered asset and the physical verification observation which exposed it. The backend model and serializer explicitly allow this combination when the observation belongs to that asset. F16 reproduced it through a real verification discrepancy and the public findings endpoint. The DTO now rejects only findings with neither reference; a regression test covers both references. The same-asset golden assurance flow then passed through public finding parsing and review/resolution. This is the only P1 observed; none remains.

## Safe release statements

Accounting can be described as **IAS 16-aligned fixed-asset workflows** with componentized capitalizable acquisition costs, straight-line depreciation, accounting-period posting, carrying-value tracking and disposal gain/loss. Do not claim full IFRS compliance. Limitations include SLM only, no component depreciation, estimate-revision workflow, IAS 36 impairment ledger, decommissioning obligations or multi-currency accounting.

Security can be described as JWT authentication, tenant-scoped and role-based authorization, department scoping, backend-authoritative permissions, an application audit trail, private evidence/export access, and size/SHA256 readback integrity verification. Do not claim a cryptographic audit ledger, malware scanning, CDR, MFA, SSO, immediate JWT revocation, certification or production penetration testing.

Measured performance statement: F15 reduced the authenticated App chunk from 605.50 kB / 119.84 kB gzip to 102.56 kB / 24.87 kB gzip, with an approximately 80.65 kB largest route and no Vite 500 kB advisory. This is a bundle-size/loading fact, not a throughput or scale guarantee.

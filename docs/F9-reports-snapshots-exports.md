# F9 — Reports, snapshots, and durable exports

## Audited contract

The reporting app exposes a role-filtered catalog at `GET /api/v1/reports/`, live report results at `/api/v1/reports/{report_type}/`, durable snapshots at `/api/v1/report-snapshots/`, and durable export jobs at `/api/v1/report-exports/`. It currently registers 17 report types: `asset_register`, `acquisitions`, `depreciation`, `accounting_periods`, `assignments`, `transfers`, `work_orders`, `maintenance_costs`, `maintenance_records`, `disposals`, `verification_campaigns`, `verification_records`, `verification_exceptions`, `assurance_runs`, `assurance_findings`, `assurance_occurrences`, and `lifecycle_history`. The catalog supplies user-facing labels, columns, supported filter names, and whether snapshot capture is supported.

Live results are current database queries, tenant and role scoped by Django, ordered by primary key, and paginated at 25 rows (maximum 100). Supported filters vary by report and are disclosed by the catalog: department, status, date range, asset tag, and search where applicable. Decimal values are serialized as exact strings. The frontend renders the catalog's column order and validates each row against it. It never builds report rows by joining cached assets or other browser data.

## Snapshot behavior

Snapshot creation accepts a report type, validated filters, and a client UUID idempotency key. Keys are unique within an organization; reusing a key with different report inputs is rejected. Repeating a queued request safely re-enqueues the same snapshot ID. Request-time role and department scope are frozen on the snapshot. The task captures within a PostgreSQL `REPEATABLE READ` transaction; `as_of` is the transaction capture timestamp, not a claim that arbitrary prior state can be reconstructed. Rows are immutable, ordered by one-based ordinal, and published with `COMPLETED` metadata in the transaction. Captures are limited to 25,000 rows; an oversized request fails and directs the caller to narrow its filters. Failed captures expose no completed row set.

Snapshot states are `QUEUED`, `RUNNING`, `COMPLETED`, and `FAILED`. Metadata includes request/start/capture/generation/failure times, row count, summary, and schema version. Rows are only served after completion. Version 1 is supported by this frontend; any other positive version remains visible as metadata, but its rows and exports are withheld. The API does not expose requester identity or the snapshot idempotency key in list/detail responses. After an ambiguous creation, the client checks scoped history and retains the same key; a matching row is treated as a candidate only, then an explicit retry with that same backend-idempotent key resolves the original request safely.

## Export behavior and private files

An export requires a completed snapshot and a supported frozen schema. Formats are `CSV` and `JSON`. M10.6's version-1 column/type registry is frozen separately from live report definitions. CSV output protects text fields against spreadsheet formula injection while preserving negative numeric decimals. JSON uses a stable versioned envelope containing snapshot metadata, columns, and rows. The frontend does not generate, rewrite, or upload either durable format.

Export jobs are `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`, or `EXPIRED`. Organization-scoped idempotency prevents duplicate creation for the same key and parameters. Celery claims a generation token, renders from immutable snapshot rows outside database transactions, stores to the private storage backend, reads the object back to verify byte size and SHA256, then publishes `COMPLETED` in a short transaction only if the attempt token is still current. Recovery requeues stale work after its grace period; stale attempts cannot publish. The backend exposes expiry (configured retention defaults to 30 days), schema version, source snapshot, row count, byte size, hash, and safe failure metadata. It never serializes its private storage key.

Download uses authenticated `GET /api/v1/report-exports/{id}/download/`. Django checks tenant/report scope, completion, expiry, and stored-file integrity before returning bytes; database `COMPLETED` status gates download. F9 fetches bytes through the authenticated API client, verifies size and SHA256 again in the browser, derives a sanitized filename from `Content-Disposition`, creates a Blob URL only after validation, and revokes it after the user-initiated download. No bucket or storage URL is exposed.

## Frontend, security, and operations

`reportDtos.ts` strictly validates report identifiers, catalog metadata, paginated row values, UUIDs, timestamps, counters, statuses, formats, hashes, and nullable metadata. Financial fields remain strings; a financial value returned as a JavaScript number fails contract validation. `reportRepository.ts` calls the real catalog/live/snapshot/export/content routes. `reportQueries.ts` uses user and session-generation query keys, invalidates only reporting data, polls queued/running snapshots and exports every four seconds, and stops when visible jobs become terminal. Authenticated binary downloads also fence session changes before and after body reads.

The Django Reports Center has Live reports, Snapshots, and Exports sections. It supports actual server filters, pagination, request status, immutable row inspection, CSV/JSON requests from selected completed snapshots, and authenticated downloads. Dynamic tables use catalog columns, safe React text output, horizontal overflow, exact string-based decimal grouping, and clear null/boolean/date rendering. Unsupported schemas and row/catalog mismatches fail closed. Mock mode retains its existing mock Reports Center; Django mode uses only reporting endpoints and never falls back to mock rows.

Django derives organization scope and enforces report permissions. Admins and asset managers have the full catalog; accountants receive financial reports and only permitted assurance slices; department managers receive operational department reports and snapshots scoped to their department; employees are denied. Snapshot rows and exports inherit the scoped parent snapshot. React role gates only improve the UI. No asset/acquisition/depreciation cache is invalidated because reporting and capture do not mutate operational data.

Snapshot/export POST calls disable automatic retries through the shared API client. Exports can be reconciled exactly by the exposed idempotency key in export history. Snapshot history omits its key/requester, so the UI will not claim a matching request is certainly its own: it retains the original key, shows uncertainty, and requires explicit recheck/retry. A retry reuses that key and Django returns the same snapshot or a parameter conflict. Session generation is checked around reconciliation and download. Failure messages do not expose tracebacks.

## Smoke and validation

Run `python scripts/f1-smoke.py --f9` with the repository virtual environment and configured PostgreSQL connection. The runner creates a random `assetflow_f9_*` database and a separate random private-storage directory under the system temp directory. Smoke-only settings execute actual registered Celery tasks eagerly. The TypeScript repositories use JWT over HTTP to Django; the F9 fixture runs `asset_register`, captures schema-v1 rows, changes the asset name afterward, proves the live query changes while the snapshot row stays frozen, creates CSV and JSON exports from that snapshot, downloads both through the authenticated endpoint, and checks content, envelope, file size, and SHA256. Python verifies database snapshot/export references and audit events. The runner removes only those disposable resources; the application database and repository remain untouched.

F9 makes no reporting business-logic, model, migration, or OpenAPI changes. Its smoke-only Celery/storage configuration and extension to the existing smoke runner are the only backend-side changes. Remaining contract limitation: snapshot requester and idempotency key are not returned, so exact correlation after a lost snapshot response relies on reusing that same key with Django. No F10 audit/lifecycle interface, F13 dashboard analytics, M11/AI, or Airflow/PySpark frontend work is included.

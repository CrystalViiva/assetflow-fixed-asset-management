# Security model and deployment limits

## Authentication

The API uses Django SimpleJWT bearer access tokens and rotating refresh tokens. The frontend keeps the access token in memory and the refresh token in sessionStorage. Session generation scopes queries and prevents stale responses from crossing logout or account switches. A failed refresh clears the browser session.

There is no immediate server-side JWT revocation mechanism for an already issued access token. Backend authentication, authorization checks, refresh rotation/blacklisting, and token expiry remain authoritative.

## Authorization and tenant scope

The authenticated Django user determines organization scope. Role and department permissions are enforced in backend permission classes, querysets, serializers, and domain services. Frontend navigation gating is only a usability aid. Object detail/action endpoints also apply server-side scope; a guessed UUID is not intended to grant access.

The application has tenant roles ADMIN, ASSET_MANAGER, ACCOUNTANT, DEPARTMENT_MANAGER, and EMPLOYEE. Django superuser/staff privilege is separate from ordinary tenant administration. There is no general-purpose Django permission editor in the product.

## Mutation integrity

Consequential actions use explicit domain services and state transitions. Transactions, row locks, database uniqueness/check constraints, and server-calculated values protect accounting and workflow records. Frontend mutations disable automatic retry where replay could create duplicate durable outcomes; uncertain HTTP results are reconciled against backend state.

Audit events are generated by domain operations. Ordinary application ORM update/delete paths are rejected for audit history, but the database is not a cryptographic append-only ledger and direct database-owner access is outside that protection.

## Private evidence and exports

Verification evidence and report exports use a private storage alias. Storage identity is generated by the server. Reads go through authenticated, organization-scoped endpoints. The browser is not given a public media URL or storage key. Upload/export workflows verify size and SHA256 during storage readback.

Evidence validation checks supported file structures and content integrity. There is no malware or antivirus scanning, content disarm/reconstruction, or guarantee that a structurally valid file is safe to open.

## Browser boundary

The public landing page does not fetch tenant dashboard, asset, report, audit, or user data. Return destinations are validated as internal routes. A 403 remains an authorization response and does not masquerade as logout. Vite variables are public build configuration; never put credentials or private keys in VITE_* values.

## Deployment checklist

- Generate unique secret and database credentials outside source control.
- Keep DEBUG false, set exact allowed hosts, and terminate TLS at a trusted reverse proxy.
- Forward HTTPS information only from the trusted proxy and do not expose the Django container directly to the Internet.
- Restrict PostgreSQL and Redis to private networks.
- Use durable, backed-up private storage for evidence and exports; never mount it into the static frontend.
- Back up PostgreSQL and private files together according to the deployment's retention and recovery policy.
- Restrict access to Swagger/OpenAPI and Django admin at the edge if the deployment does not intend to publish them.
- Monitor database, worker, Beat, disk, and private-storage health. This repository does not provide a hosted monitoring service.

## Not claimed

AssetFlow has no MFA, SSO, immediate access-token revocation, malware scanning, CDR, cryptographic audit chain, SOC 2/ISO certification, or independent production penetration-test result. These controls must not be implied in portfolio or deployment copy.
